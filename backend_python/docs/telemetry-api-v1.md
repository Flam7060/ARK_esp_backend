# Telemetry API v1 — сбор данных с клиента

Область документа: приём и хранение игровых наблюдений (постройки, позиции
игроков/дино) от клиента `ark_fun_tools`, плюс — с этой версии — живой обмен
позициями союзников между клиентами трайба (§7). Аутентификация, лицензии,
группы/трайбы как отдельные сущности — в другом документе; здесь они входят
только как предположения (assumptions) о том, что уже известно на момент
приёма телеметрии.

**Два независимых канала, не один:**

| | Архив/карта (§1-6) | Живой обмен позициями (§7) |
|---|---|---|
| Транспорт | HTTP, пачками по таймеру | WebSocket, постоянное соединение |
| Сервис | `ark_backend` (Python/FastAPI) | `ark_relay` (Go, отдельный сервис) |
| Частота | постройки — минуты, позиции — секунды | секунды (то же, но без записи) |
| Гарантии | атомарный снимок, идемпотентность | доставки нет гарантии, актуальность важнее |
| Хранит историю | да (Postgres) | нет — только транзит между клиентами |

Решение по транспорту живого канала — WebSocket, а не UDP и не gRPC — с
обоснованием и отвергнутыми альтернативами в §7.4.

Источник полей — фактическая структура `game.Target` в клиенте
(`client/internal/engine/game/tracker.go`) и её аналог в референсном тулze
(`ActorRecord`/`TurretInfo`). Ничего из полей ниже не придумано — либо оно уже
читается клиентом, либо явно помечено как «нужно будет добавить в клиент».

---

## 1. Предположения (assumptions)

- **A1.** К моменту вызова телеметрии клиент уже аутентифицирован и несёт
  `client_id` (uuid клиента) и `tribe_id` (группа, к которой привязан аккаунт)
  в JWT. Сама выдача JWT — предмет отдельного документа по AUTH.
- **A2.** Один HTTP-клиент = один игровой процесс `ShooterGame.exe` на одной
  карте/сервере ARK в один момент времени. `server_id`/`map_id` передаётся
  клиентом явно (см. §5) — сервер бэкенда не может вывести это сам, движок
  такого идентификатора наружу не отдаёт.
- **A3.** Позиции — «сырые» игровые единицы (unreal units), не метры. Деление
  на 100 (единицы → метры) — обязанность потребителя (фронтенда карты), не
  бэкенда: хранить нужно то, что реально прочитано, конвертация — вопрос
  отображения.

## 2. Термины

| Термин | Значение |
|---|---|
| Наблюдение (observation) | Один факт о состоянии объекта в конкретный момент времени, присланный конкретным клиентом. |
| Объект (entity) | Постройка, игрок или дино в игровом мире. У объекта нет стабильного ID в памяти игры — см. §4.1. |
| Снимок (snapshot) | Пачка наблюдений, собранная клиентом за один цикл `Rebuild`/`Poll` и отправленная одним запросом. |
| Репортёр (reporter) | Клиент/аккаунт, приславший снимок. Не путать с объектом наблюдения. |

---

## 3. Функциональные требования

**Приём данных**

- **FR-1.** Система принимает пакетную отправку наблюдений (snapshot), а не
  одно наблюдение за запрос. Клиент шлёт данные раз в `N` секунд
  (конфигурируемо, по умолчанию не чаще раза в 5–10 секунд для построек и раз
  в 1–2 секунды для позиций живых — см. FR-8 про разные частоты).
- **FR-2.** Приём идемпотентен: повторная отправка того же снимка (сетевой
  ретрай) не создаёт дублей. Идемпотентность — по `snapshot_id` (uuid,
  генерируется клиентом один раз на снимок).
- **FR-3.** Каждое наблюдение содержит `observed_at` — время на клиенте
  (UTC, ISO-8601), не время получения сервером. Часовой дрейф клиента —
  забота клиента (NTP), сервер полю доверяет как есть, но отдельно пишет
  `received_at = now()` для отладки рассинхрона.
- **FR-4.** Отношение (`Rel` — свой/враг/дикий) **не принимается от клиента
  как факт**. Клиент присылает объективные поля игры (`team`, `tribe_name`),
  а вычисление отношения к конкретному трайбу — задача бэкенда при чтении, а
  не при записи. Причина: `Rel` в `game.Target` уже посчитан относительно
  *локального игрока конкретного клиента* — у другого члена того же трайба
  то же самое TargetingTeam может значить другое отношение, если клиенты
  смотрят из разных трайбов одного кластера. Хранить чужой вывод как факт —
  значит закрепить ошибку одного клиента для всех читателей.
- **FR-5.** У построек нет стабильного ID из памяти игры — `Addr` невалиден
  между перезапусками процесса и переиспользуется в течение одной сессии.
  Идентичность постройки на бэкенде — составной ключ (`tribe_id`, `map_id`,
  `class`, координата с округлением до `dedup_radius`, по умолчанию 300
  игровых единиц — постройки не двигаются, и два наблюдения одной постройки в
  разные моменты почти всегда лягут в один и тот же квадрат). Округление, а
  не точное совпадение координат: одна и та же постройка на двух снимках
  подряд может дать координату с точностью до сантиметра разной из-за
  плавающей точки при чтении памяти.
- **FR-6.** У игрока/дино идентичность — тоже не `Addr`. Ключ на запись:
  (`tribe_id` репортёра как namespace, `label`, `observed_team`). Слияние
  дублей по имени — на бэкенде, не на клиенте: клиент своей историей других
  клиентов не располагает.
- **FR-7.** Наблюдения о постройках *своего* трайба (совпадает `tribe_id`
  репортёра и `tribe_name` объекта) хранятся с полной детализацией (боезапас,
  топливо, число предметов). Наблюдения о постройках/юнитах чужих трайбов —
  только то, что видно снаружи: позиция, класс, отношение по team. Разделение
  выполняется на этапе приёма (валидация payload), не постфактум.
- **FR-8.** Частота записи разная для разных категорий и настраивается на
  бэкенде, а не жёстко зашита в клиенте:
  - постройки — снимок раз в конфигурируемый интервал (минуты), они не
    двигаются;
  - позиции живых своего трайба — чаще (секунды), это активность, а не карта;
  - позиции чужих — согласно решению, отмеченному как открытый вопрос в §9 (в
    этом документе трактуется как «разреженные точки», не непрерывный трек —
    см. UC-3).
- **FR-9.** Приём отклоняет снимок целиком (весь `snapshot_id`), если
  подпись/JWT не проходит проверку либо `tribe_id` в токене не совпадает с
  `tribe_id`, заявленным в payload для «своих» построек. Частичный приём
  (часть объектов приняли, часть — нет) не предусмотрен: снимок — атомарная
  единица.
- **FR-10.** Хранится версия схемы клиента, приславшего снимок
  (`client_version`), чтобы при миграции формата поля можно было понять,
  какие старые снимки в каком виде лежат в базе.

## 4. Use cases

### UC-1 — Снимок построек своего трайба

- **Актор:** клиент `ark_fun_tools`, участник трайба.
- **Предусловие:** клиент аутентифицирован, `Rebuild` завершился, есть список
  `Target{Cat: CatStructure|CatTurret}` с `Tribe == "имя своего трайба"`.
- **Основной поток:**
  1. Клиент раз в интервал построек собирает все свои постройки в один
     `StructureSnapshot` (§5.2).
  2. Отправляет `POST /v1/telemetry/structures`.
  3. Бэкенд проверяет JWT и совпадение `tribe_id`.
  4. Для каждой постройки — upsert по ключу из FR-5: если постройка уже
     известна (тот же класс+координата в радиусе), обновляется её последнее
     состояние (боезапас/топливо/предметы) и `last_seen_at`; если нет —
     создаётся новая запись и `first_seen_at`.
  5. Постройки трайба, не встреченные ни в одном снимке дольше
     `stale_after` (конфигурируемо, например 24 часа) — не удаляются
     автоматически, а помечаются `status = possibly_demolished` для ручной
     проверки: снос неотличим от «клиент был выключен весь день».
- **Постусловие:** карта построек трайба отражает последнее известное
  состояние каждой постройки.
- **Исключения:** координата вне разумных пределов карты (`|x|,|y|,|z| >
  max_world_coord`) — объект снимка отбрасывается, снимок в остальном
  принимается (см. отличие от FR-9: это валидация одного объекта внутри
  снимка, а не подписи всего снимка).

### UC-2 — Живые позиции союзников (свой трайб)

- **Актор:** клиент `ark_fun_tools`.
- **Предусловие:** есть `Target{Cat: CatPlayer|CatDino, Tribe: свой трайб}`.
- **Основной поток:** не HTTP-снимок, а живой канал §7 — сущности своего
  трайба уходят в Redis (§8.1) через `ark_relay`, TTL вместо истории.
- **Постусловие:** видно, кто из трайба сейчас в игре и где; траектории за
  период — **не факт этой версии**, см. открытый вопрос §9.1: если она
  всё же нужна, это отдельная таблица (условно `ally_position_log`),
  дозаписываемая либо из `ark_relay` при каждом входящем сообщении, либо
  отдельным HTTP-снимком, как было в первой версии этого документа — обе
  реализации совместимы с остальной схемой, выбор не блокирует всё
  остальное здесь.
- **Примечание:** это данные о *согласившихся* пользователях (участник
  своего же трайба, установивший тот же клиент) — не требует отдельного
  этического решения в отличие от UC-3.

### UC-3 — Снимок позиций противника (открытый вопрос, см. §9)

- **Актор:** клиент `ark_fun_tools`.
- **Предусловие:** `Target{Rel: RelEnemy|RelStranger}` в поле зрения клиента
  (то есть в пределах того, что и так прислал игровой сервер этому клиенту —
  без этого клиент физически не может прочитать позицию).
- **Основной поток:** снимок содержит **последнюю** позицию с меткой
  времени, не непрерывный поток. Читающий клиент (другой участник трайба) при
  входе в зону, где по последним данным был враг, получает отметку
  «последний раз замечен здесь в ЧЧ:ММ» — а не текущую позицию (её нет,
  враг мог уйти). Как только сам читающий клиент видит цель напрямую —
  локальные, живые данные полностью перекрывают отметку с бэкенда: это
  правило клиентского рендера (esp/оверлей), не API, здесь только оговорено,
  откуда исходит отметка, если своей у клиента ещё нет.
- **Постусловие:** участники трайба видят не «радар врагов реалтайм», а
  «где в последний раз кто-то из трайба его видел» — принципиально более
  слабая гарантия, и это осознанное ограничение, а не недоработка API.

### UC-4 — Чтение карты (фронтенд/веб-клиент)

- **Актор:** аутентифицированный пользователь трайба, веб-интерфейс.
- **Основной поток:** `GET /v1/tribes/{tribe_id}/structures?map_id=...` и
  `GET /v1/tribes/{tribe_id}/positions?since=...` — пагинированные выборки,
  не «отдать всё за всё время» (см. §6 про пагинацию).

## 5. Шаблоны данных (payload)

Соглашения: `snake_case` в JSON (совпадает со стилем FastAPI/pydantic),
координаты — `float`, время — ISO-8601 UTC со смещением `Z`, все
идентификаторы объектов — `string` (uuid), а не числа (см. §6).

### 5.1 Общий конверт снимка

```json
{
  "snapshot_id": "b3f1c2a0-9e2e-4b7a-9a1e-2f9a7c0e1234",
  "client_id": "3d9a3e2a-1111-4a2b-8c3d-abcdef123456",
  "client_version": "1.4.0",
  "tribe_id": "8f2a1c00-2222-4c3d-9e1f-abcdef654321",
  "server_id": "ase-official-pvp-1234",
  "map_id": "TheIsland",
  "observed_at": "2026-08-28T14:03:11.500Z",
  "kind": "structures",
  "items": [ /* см. 5.2 / 5.3 / 5.4 в зависимости от kind */ ]
}
```

`kind` — один из `structures | ally_positions | enemy_positions`. Разные
`kind` в одном снимке не смешиваются: у них разная частота (FR-8) и разная
валидация (FR-7), совмещать — значит терять возможность гонять их разными
интервалами независимо.

### 5.2 Постройка (`kind: "structures"`)

Источник полей: `game.Target` (`Cat: CatStructure|CatTurret`) +
`fields.go` (`ammo`, `range`, `fuel`, `enabled`, `powered`).

```json
{
  "class": "AutoTurret_C",
  "kind_hint": "turret_auto",
  "x": 12345.6, "y": -9876.5, "z": 234.1,
  "tribe_name": "Дружина",
  "team": 42,
  "item_count": null,
  "has_item_count": false,
  "turret": {
    "ammo": 480,
    "range": 3000.0,
    "enabled": true,
    "powered": true
  }
}
```

- `kind_hint` — вывод твоего `RuleClassifier` на клиенте (`Kind(class)`).
  Присылается как подсказка, но бэкенд не обязан ей доверять вслепую:
  правила могут измениться в новой версии клиента, и переклассификация
  задним числом должна быть возможна на сервере без переотправки данных
  клиентом. Поэтому `class` (сырое имя) — обязателен и первичен, `kind_hint`
  — опционален и вторичен.
- `turret` — присутствует только если `Cat == CatTurret`; для прочих
  построек это `null`, а не объект с нулями (нельзя путать «нет турели» с
  «турель с нулевым боезапасом»).
- `item_count`/`has_item_count` — калька `Target.ItemCount/HasItemCount`;
  оба поля обязательны, потому что вопрос «пусто или не прочитано» разный.

### 5.3 Позиция союзника (`kind: "ally_positions"`)

```json
{
  "label": "Kesha",
  "class": "PlayerPawnTest_Female_C",
  "cat": "player",
  "team": 42,
  "tribe_name": "Дружина",
  "x": 12000.0, "y": -9000.0, "z": 200.0,
  "health": 850.0, "max_health": 1000.0,
  "level": 105,
  "sleeping": false,
  "dead": false
}
```

`cat` — `"player" | "dino"`, калька `game.Category.String()`
(category.go:26-34) — тот же словарь, чтобы не заводить второй на бэкенде.

### 5.4 Позиция противника (`kind: "enemy_positions"`)

Урезанная версия 5.3 — то, что *объективно* видно снаружи, без внутренних
для трайба вещей:

```json
{
  "label": "Kesha",
  "class": "PlayerPawnTest_Female_C",
  "cat": "player",
  "team": 17,
  "x": 12000.0, "y": -9000.0, "z": 200.0,
  "last_seen_by_client_at": "2026-08-28T14:03:09.100Z"
}
```

Нет `health`/`level`/`tribe_name` — это не сокрытие ради экономии трафика, а
следствие FR-7: клиент физически не обязан присылать о чужих больше, чем
нужно для UC-3 (последняя точка на карте), и меньшая поверхность — меньше,
что может утечь при компрометации аккаунта одного члена трайба.

## 6. Стандартизация API

- **Версионирование:** префикс `/v1/...`, совпадает с уже существующей
  структурой `routers/v1` в `ark_backend`. Ломающие изменения формата —
  новый префикс `/v2`, не мутация `/v1` на месте.
- **Аутентификация:** `Authorization: Bearer <jwt>` на каждый запрос, без
  исключений для телеметрии — это не публичный эндпоинт.
- **Идентификаторы:** везде `uuid` как строка, не автоинкрементный `int`.
  Причина: `snapshot_id` генерируется клиентом до похода в сеть (для
  идемпотентности, FR-2), а автоинкремент клиент сгенерировать не может.
- **Пагинация чтения:** курсорная (`?cursor=...&limit=...`), не
  `offset/limit` — история позиций растёт непрерывно, и `offset` на
  растущей таблице даёт то дубли, то пропуски между запросами страниц.
- **Конверт ошибки** (единый для всех эндпоинтов):
  ```json
  {
    "error": {
      "code": "invalid_tribe_scope",
      "message": "tribe_id в токене не совпадает с tribe_id объекта",
      "details": {}
    }
  }
  ```
  `code` — стабильная машиночитаемая строка (клиент может ветвиться по ней),
  `message` — для лога/отладки, не для показа игроку как есть.
- **Ограничение размера снимка:** `items` не более `max_items_per_snapshot`
  (например, 2000) — на базе с полутора тысячами построек один снимок и так
  подходит к пределу; жёсткий потолок нужен, чтобы модифицированный клиент
  не мог прислать снимок на гигабайт.
- **Частичная валидация внутри снимка:** объект с плохими данными
  (координата вне мира, обязательное поле пусто) отбрасывается сам, снимок в
  остальном принимается, а в ответе перечисляются пропущенные индексы:
  ```json
  { "accepted": 1180, "rejected": [ { "index": 42, "code": "coord_out_of_bounds" } ] }
  ```
  Это отличается от отказа всего снимка при неверном JWT/`tribe_id` (FR-9) —
  там нарушение уровня доверия ко всему снимку, здесь — брак в одной записи.

## 7. Живой канал: обмен позициями союзников (`ark_relay`, Go)

Отдельный сервис, не эндпоинт `ark_backend`. Причина разделения — не только
язык: это два процесса с принципиально разным профилем нагрузки. `ark_backend`
обслуживает короткие stateless HTTP-запросы (запрос — ответ — забыл). Этот
канал держит тысячи одновременных долгоживущих соединений и стейт по каждому
(кто в каком трайбе, кому релеить) — смешивать это с обработкой HTTP в одном
процессе значит, что нагрузка на одно убивает отзывчивость другого.

### 7.1 Почему Go, а не Python/FastAPI

- Клиент `ark_fun_tools` уже на Go — общие типы сообщений (см. 7.3) можно
  переиспользовать в клиенте и в релее без второго описания схемы на другом
  языке.
- Горутина на соединение — естественная модель именно для этой задачи
  (тысячи держащихся сокетов, лёгкое переключение), тогда как в Python это
  либо asyncio с ручным управлением тысячами корутин, либо процесс на
  соединение — то, ради чего Go и выбирают под такой профиль нагрузки.
- Сервис маленький и без пересекающейся ответственности с `ark_backend`
  (не трогает Postgres, не делает бизнес-логику лицензий) — polyglot здесь
  не создаёт проблему согласования миграций/моделей, которая обычно и есть
  главный довод против нескольких языков в одном бэкенде.

### 7.2 Что делает `ark_relay`, а что — нет

- Держит один WebSocket на онлайн-клиента.
- Принимает от клиента **список того, что клиент прямо сейчас видит через
  ESP** — не только позицию своего персонажа. Правка по сравнению с первой
  версией этого раздела: цель («поделиться с трайбом тем, что видит один
  клиент») требует делиться и союзниками, и дино, и противниками, попавшими
  в область прогрузки именно этому клиенту — иначе смысл живого канала
  сводится к «кто онлайн», а не к расширению обзора трайба за пределы того,
  что видит каждый его участник по отдельности.
- **v2: релеит принятое подписчикам той же пары `(group_id, server_ip)`, не
  `tribe_id`.** Sharing group (`sharing_group`/`group_member`,
  `backend_python`) — реальный круг доверия: один аккаунт может играть в
  разные ARK-трайбы на одном сервере и делиться с одними и теми же людьми
  через приложение вне зависимости от того, в каком трайбе кто сейчас
  состоит. Но одной группы мало — двум членам группы на разных
  серверах/картах нечем делиться друг с другом вживую (их сайтинги про
  разные миры), поэтому комната — пересечение группы и сервера. Игровой
  трайб (`Entity.tribe`) остался полем данных наблюдаемой сущности, не
  единицей маршрутизации.
- Членство в группе — Redis SET `ark:group:{group_id}:members`,
  поддерживаемый `backend_python`'s `sharing_service.py` в актуальном
  состоянии (полный слепок Postgres `group_member`, не разовые инкременты);
  проверяется на каждый коннект (`SISMEMBER`), а не через поход в
  `ark_backend`. Кик/выход/удаление группы дополнительно шлёт
  `PUBLISH ark:group:{group_id}:revoked {account_id}` — `ark_relay`
  подписан на этот канал (`PSUBSCRIBE ark:group:*:revoked`) и рвёт уже
  открытое соединение почти сразу, не дожидаясь истечения JWT.
- **v3: `group_id` больше не query-параметр хендшейка — клиент его вообще
  не передаёт.** Один аккаунт имеет ровно одну активную группу
  (`account.active_group_id`, Postgres, зеркалится в Redis
  `ark:account:{account_id}:active_group` через `group_cache.py`) —
  `ark_relay` резолвит её сам по `account_id` из JWT/API-key на
  хендшейке; клиент без активной группы получает 403. `active_group_id`
  выставляется автоматически при создании/вступлении в группу
  (`sharing_service.create_group`/`join_group`) и снимается при
  выходе/кике/удалении группы, если она была активной
  (`sharing_service.leave_group`/`remove_member`/`delete_group`); также
  доступен явный `POST /v1/accounts/me/active-group` для переключения
  между несколькими группами, в которых состоит аккаунт. Причина этого
  костыля-удаления: `group_id` как клиентский параметр требовал, чтобы
  клиент "знал", в какой группе он сейчас работает, — состояние, которое
  и так уже целиком на сервере (Postgres), дублировать его на клиенте
  было лишней точкой рассинхронизации без пользы.
- По каждой сущности — последнее сохранённое состояние в Redis (§8.1), с
  TTL: если ни один клиент комнаты не видит сущность дольше TTL, она сама
  пропадает с карты, без явного события «пропал» *в этом канале* (для
  Postgres-копии явный сигнал есть — см. §8.1a).
- **Категории расширены структурами и турелями** (были только
  player/dino) — источник контракта: DTO клиента `arkmultitool`
  (`kopt::share::Sighting`/`TurretInfo`, `include/kopt/share.hpp`).
  Структуры/турели раньше не проходили через этот канал вовсе (отдельный
  HTTP-пайплайн прямо в `backend_python`); этот пайплайн (§6, FR-5) остаётся
  как есть для существующих клиентов, `ark_relay` — дополнительный путь, не
  замена.
- **Не пишет ничего в Postgres напрямую.** Живой канал сам по себе — транзит.
  Durable-копию структур пишет фоновая задача из Redis (§8.3, устаревший
  путь) или консьюмер Redis Stream (§8.1a, актуальный путь для новых
  сущностей) — не сам relay.
- Не хранит состояние дольше жизни соединения на своей стороне — состояние
  сущностей живёт в Redis (§8.1), а не в памяти процесса `ark_relay`: при
  перезапуске/масштабировании на несколько инстансов relay ничего не теряет,
  потому что сам ничего и не хранил.

### 7.3 Протокол

Аутентификация — тот же JWT, что уже выдал `ark_backend` при логине, но
**v2 сократил claims до одного `account_id`** — ни `tribe_id`, ни
`client_id` в токене больше нет. Причина: группа — не то, что застыло на
момент выдачи токена (вступить/выйти/кикнуть можно в любой момент), а
переиздавать JWT на каждую мутацию членства значило бы связать два
независимых процесса именно там, где связывать их не нужно. `server_ip`
вместо этого — query-параметр хендшейка (`?server_ip=...`, обязателен,
иначе 400 ещё до проверки токена); группа же клиентом вообще не
передаётся (§7.2, v3) — активная группа резолвится живьём по Redis на
каждый коннект по `account_id` из токена. Игровые факты о сессии (какой персонаж, какое племя) едут в теле
сообщений (`reporter_character_id`, `Entity.tribe`), а не в токене — клиент
источник истины для своего игрового состояния, JWT — только доказательство,
какой аккаунт говорит.

Handshake — обычный HTTP-апгрейд на WebSocket; нативный Go-клиент передаёт
токен заголовком `Authorization`, веб-клиент (если появится) — query-параметром
`?token=...`, потому что браузерный `WebSocket` API не даёт ставить
произвольные заголовки на хендшейк. `ark_relay` проверяет подпись JWT сам,
без обратного похода в `ark_backend` на каждое подключение — если подпись
асимметричная (см. AUTH-документ), релею достаточно публичного ключа в
конфиге.

Сообщения — JSON, симметрично в обе стороны. Одно сообщение от клиента несёт
пачку сущностей за один тик — те же объекты, что и `ally_positions`/
`enemy_positions` из §5.3-5.4, но без архивных полей и чаще:

```json
// клиент -> relay, раз в 1-2 секунды
{
  "type": "sighting",
  "seq": 4821,
  "entities": [
    { "key": "player:Kesha:42", "cat": "player", "team": 42,
      "label": "Kesha", "x": 12000.0, "y": -9000.0, "z": 200.0 },
    { "key": "player:Vasya:17", "cat": "player", "team": 17,
      "label": "Vasya", "x": 12500.0, "y": -8800.0, "z": 210.0 }
  ]
}
```

```json
// relay -> остальным клиентам с той же активной группой и server_ip
{
  "type": "sighting",
  "reported_by": "3d9a3e2a-1111-4a2b-8c3d-abcdef123456",
  "relayed_at": "2026-08-28T14:03:11.500Z",
  "entities": [ /* тот же формат, что и во входящем сообщении */ ]
}
```

- `key` — тот же составной идентификатор сущности, что и в FR-6
  (`cat:label:team`), не `Addr`: relay не в игровом процессе, читать сырой
  адрес ему неоткуда, да и не нужно — идентичность через игровые данные
  работает одинаково что на бэкенде, что здесь. **v2**: для `structure`/
  `turret` это поле может прийти пустым — relay сам вычисляет
  `{cat}:{contentHash}` (класс + округлённые до 300 единиц координаты, тот
  же радиус, что и FR-5) до валидации, у построек нет игрового отображаемого
  имени, из которого клиент мог бы сам собрать такой ключ.
- `seq` — монотонный счётчик тиков **клиента-отправителя**, не отдельной
  сущности внутри пачки: подтверждает, что вся пачка не старее последней
  принятой, а не разбирает пачку по сущностям — так проще, и на кадансе в
  секунды переупорядочивание одной сущности внутри пачки не тот случай, ради
  которого стоит городить `seq` на каждую запись.
- **v2**: `cat` расширен до `player | dino | turret | structure`; `turret`
  требует вложенный объект `turret` (ammo/range/targeting/warning/powered/
  active/targeting_actor — зеркало `kopt::share::TurretInfo` клиента
  `arkmultitool`); `structure`/`turret` требуют `class` вместо `label`.
  Полная схема — `backend_go/docs/asyncapi.yaml` (каноническая, синхронна с
  `internal/protocol/message.go` построчно), здесь не дублируется во
  избежание расхождения.
- **v2**: входящее сообщение может нести `reporter_character_id` (игровой id
  персонажа отправителя — данные сессии, не идентичность) и `vanished`
  (список `key`, которые клиент раньше видел и в этом батче не видит —
  явный сигнал «пропало» для Postgres-копии, см. §8.1a).
- Отдельный `type: "ping"/"pong"` — раз в интервал (например 30 секунд) для
  вычищения мёртвых соединений: TCP сам по себе не скажет релею, что клиент
  вылетел без корректного закрытия (крэш, потеря сети без FIN).

### 7.4 Отвергнутые варианты и почему

- **UDP.** Разбирали отдельно: оправдан на частотах в десятки герц, где
  оверхед TCP/WS реально заметен и где устаревание важнее гарантии доставки
  настолько, что стоит писать свой протокол поверх. При кадансе в 1-2 секунды
  для человеко-читаемых оповещений этой разницы нет, а цена — свой бинарный
  протокол, HMAC на пакет, отдельный UDP-listener (FastAPI/обычный HTTP-сервер
  UDP не слушает), и худшая проходимость через файрволы по сравнению с
  портом 443. Ничего из этого не окупается на этой частоте.
- **gRPC.** Не альтернатива UDP (gRPC — поверх HTTP/2, то есть TCP) и не
  подходит для канала браузер↔сервер напрямую (нужен grpc-web прокси). Как
  замена REST/JSON для архивного канала (§1-6) — валидный вариант, но
  добавляет второй тулчейн (protobuf-кодогенерация для Go и Python) ради
  выигрыша, не нужного на частоте архивных снимков. Отложено, не отвергнуто
  навсегда — если типизированный контракт станет проблемой, вернуться к
  этому пункту.

## 8. Хранилище: что в Redis, что в Postgres

Правило одно: **Redis — источник истины для «сейчас», Postgres — источник
истины для «было»**. Ничего не дублируется вслепую — то, что дешевле держать
только в одном месте (живая позиция игрока — только в Redis, с TTL вместо
удаления), там и остаётся.

### 8.1 Redis — живые сущности (игроки, дино, свои и чужие)

Ключ на сущность, не на репортёра — несколько клиентов комнаты могут видеть
одного и того же врага одновременно, и должен остаться один актуальный
объект, а не по записи на каждого свидетеля.

**v2**: пространство ключей переехало с `ark:tribe:{tribe_id}:*` на
`ark:group:{group_id}:server:{server_ip}:*` вместе с переходом раздачи в
`ark_relay` на пару (группа, сервер) — см. §7.2. `server_ip` в ключе
обязателен, не только `group_id`: сеточный `Key` structure/turret (300
единиц) сам по себе не различает два разных сервера с похожим ландшафтом.

```
HASH  ark:group:{group_id}:server:{server_ip}:entity:{key}
  cat            "player" | "dino" | "turret" | "structure"
  team           int
  label          string
  x, y, z        float
  reported_by    account_id (кто прислал последним)
  updated_at     unix ms
  content_hash   последний хеш, для которого делался XADD (§8.1a) -- не
                 трогается обычным апдейтом живого вида, только дедуп-гейтом
  streamed_at    unix ms последнего XADD -- то же самое
TTL   90s   -- в 45-90 раз больше каданса (1-2с): переживает пропуск
             -- нескольких тиков подряд (лаг, кратковременная потеря сети),
             -- но не переживает реальный уход цели из вида дольше минуты.
```

`{key}` = `{cat}:{label}:{team}` для player/dino (тот же составной ключ, что
и в FR-6/§7.3) или `{cat}:{contentHash}` для structure/turret, вычисляемый
самим `ark_relay` (§7.3) — единый на всю систему: relay пишет по нему,
`ark_backend` при желании читает по нему же для «живой» карты в веб-панели
(не только через WS-push).

Индекс для перечисления «все сущности комнаты сейчас»:

```
ZSET  ark:group:{group_id}:server:{server_ip}:entities   -- score = updated_at (unix ms)
```

Обновляется той же командой, что и запись в HASH (одна Lua-транзакция или
`MULTI`, чтобы не разъезжались). Чтение — `ZRANGEBYSCORE ... (now-90000) now`,
а не `ZRANGE` целиком: попавшее туда, но просроченное, само отфильтровывается
диапазоном, без отдельной задачи на подчистку индекса. HASH-ключи всё равно
испарятся сами по TTL — рассинхрон на несколько секунд между исчезновением
из HASH и вычищением из ZSET не имеет значения, потому что читатель и так
режет по времени.

Живой HASH+ZSET сам по себе никогда не попадает в Postgres — ни отдельной
таблицей, ни периодическим снимком. **v2**: это по-прежнему верно для
позиций игроков (нет истории — см. открытый вопрос ниже), но структуры/
турели/дино теперь параллельно текут в Redis Stream (§8.1a) именно ради
Postgres-копии — два независимых механизма поверх одного источника фактов,
не один эволюционировавший в другой.

### 8.1a Redis Streams — дедуп-гейт перед Postgres (структуры, турели, дино)

Новое в v2, отдельно от §8.1: `ark_relay` XADD'ит в Redis Stream только
когда контент-хеш сущности изменился или истёк keyframe (5 минут) с
последнего XADD — не на каждый тик, как HASH выше. Смысл не в корректности
(её и так даёт `UNIQUE(server_id, object_hash)` + `ON CONFLICT DO UPDATE` в
самой Postgres-схеме — два одинаковых факта схлопнутся в одну строку сами),
а в трафике: не гонять по сети и не будить консьюмера ради факта, который
уже известен и не изменился.

Хеш — `hash/fnv` (FNV-1a) от `{cat}|{class}|{округлённые x,y,z по 300}`
(`internal/dedup.ContentHash`, `ark_relay`); **не крипто-хеш**, экономия
трафика, не защита от подмены. Осознанно исключены из хеша: `team`/`tribe`
(смена владельца — новый факт, не то же самое) и динамическое состояние
турели (`ammo`/`powered`/`active`/`targeting` — тикает поминутно, это
забота живого HASH+TTL выше, не Postgres-истории).

```
STREAM  ark:stream:structure_sighting   -- структуры и турели вместе
                                         -- (турель = структура + доп. поля,
                                         -- как и в самой Postgres-схеме,
                                         -- где ark_structure_turret --
                                         -- 1:1 расширение ark_structure)
STREAM  ark:stream:dino_sighting        -- тамед-дино
```

Консьюмер — та же инфраструктура consumer group (`XREADGROUP`/`XACK`/
`XAUTOCLAIM`, `backend_python`'s `core/redis_stream.py`), что уже проверена
в проде на `ark:stream:player_sighting` (`services/player_ingest_service.py`)
— игроки **не входят** в v2 (дедуп по контент-хешу не имеет смысла для
постоянно двигающейся сущности, а поток для игроков уже специфицирован и
ждёт продюсера отдельно). Python-модели/хендлеры для `structure_sighting`/
`dino_sighting` реализованы (`services/structure_sighting_service.py`,
`services/dino_sighting_service.py`) и подключены в `main.py`'s lifespan
рядом с player-консьюмером; проверены end-to-end живым `XADD` через реальный
Docker Compose стек (Postgres+Redis) — структура/турель/`removed=true`/дино
все доходят до `ark_structure`/`ark_structure_turret`/`tamed_dino`
корректно, `server`/`tribe` авторезолвятся по `server_ip`/`tribe_name`.

В ходе этой проверки найден и исправлен реальный баг в
`core/redis_stream.py::run_consumer`: любая ошибка `XAUTOCLAIM`/`XREADGROUP`
за пределами `redis.ConnectionError` (например, обрыв соединения при
рестарте самого Redis) раньше тихо убивала фоновый `asyncio.Task` консьюмера
навсегда — ни один `await` на эту задачу не делается до shutdown, поэтому
необработанное исключение нигде не логировалось и не всплывало (замечено
живьём: `last-delivered-id` застыл на месте без единой ошибки в логах).
Теперь обе точки ловят `Exception` широко и уходят на 5-секундный бэкофф,
не пробрасывая исключение дальше — тот же принцип восстановления, что уже
был у `redis.ConnectionError`, просто без искусственного сужения набора
причин, из-за которых консьюмер имеет право упасть.

Известный пробел: точный хеш дино по образцу `TamedDino.object_hash`
(`hash(species + gender + color_0..5)`) требует данных, которых у клиента
`arkmultitool` сегодня нет (пол/окрас) — v2 хеширует дино тем же способом,
что и структуры (класс + сетка координат), грубее задуманного. Расширение
DTO клиента под генетику — отдельная задача (нужен reverse-engineering
оффсетов в памяти игры).

**Явный сигнал «пропало» вместо только TTL/устаревания.** `Inbound.vanished`
(§7.3) — ключи, которые клиент только что перестал видеть — идёт в тот же
стрим отдельной записью с `removed=true` (`object_hash` восстанавливается
из самого ключа, `internal/dedup.HashFromKey`, без пересчёта из свежих
координат, которых у пропавшей цели уже нет). Не заменяет проверку
свежести на чтении — если снос никто не видел, сигнала не будет вообще.

**Идея на будущее для самой отрисовки (не реализуется в v2)**: вместо
бинарного `status: active | possibly_demolished` (как в устаревшей
`structure`, §8.3) — снапшот-модель. Карта показывает, что было найдено на
дату последнего наблюдения; при повторном пролёте `last_seen_at` у найденных
структур обновляется (колонка уже есть в `ark_structure`), а отрисовка
кодирует давность цветовой шкалой уверенности — от «видели только что» до
«давно не подтверждали», без единого порога и без решения «ещё существует
или уже нет» на бэкенде вообще. Естественно покрывает и снос рейдом (никто
не подтвердил → цвет тускнеет), не только распад — фиксированный порог
времени не годится в принципе: метал/тек живут неделями без визитов, дерево
— часы, а сервера меняют множитель распада произвольно.

### 8.2 Redis — постройки (кэш перед записью в Postgres)

```
HASH  ark:tribe:{tribe_id}:structure:{struct_key}
  class          string
  kind_hint      string | null
  x, y, z        float
  item_count     int | null
  has_item_count bool
  ammo, range    float | null
  enabled, powered  bool | null
  first_seen_at  ISO-8601   -- не трогается при повторных апдейтах
  last_seen_at   ISO-8601
  dirty          "1"        -- выставляется при каждой записи, снимается
                             -- фоновой задачей после переноса в Postgres
TTL   нет (или очень большой, сутки) -- постройки не эфемерны, как игроки;
      если ключ всё же вымоется по памяти до переноса — не страшно: следующий
      снимок от клиента пересоздаст его, максимум потеря — интервал между
      снимками клиента, тот же риск, что и без кэша вовсе.
```

`{struct_key}` — округлённая координата+класс из FR-5, тот же ключ и в
Postgres (§8.3), чтобы upsert был прямым переносом, не поиском соответствия.

### 8.3 Postgres — постройки (durable-копия, единственная таблица с историей)

```sql
CREATE TABLE structure (
    id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
    tribe_id        uuid NOT NULL,
    map_id          text NOT NULL,
    struct_key      text NOT NULL,   -- тот же ключ, что и в Redis (8.2)
    class           text NOT NULL,
    kind_hint       text,
    x float8, y float8, z float8,
    item_count      int,
    has_item_count  boolean NOT NULL DEFAULT false,
    ammo float8, range float8,
    enabled boolean, powered boolean,
    first_seen_at   timestamptz NOT NULL,
    last_seen_at    timestamptz NOT NULL,
    status          text NOT NULL DEFAULT 'active', -- active | possibly_demolished
    UNIQUE (tribe_id, map_id, struct_key)
);
CREATE INDEX ON structure (tribe_id, map_id) WHERE status = 'active';
```

Фоновая задача (`ark_backend`, периодическая — Celery beat/APScheduler,
интервал независим от частоты клиентских снимков, например раз в 5 минут):

1. `SCAN` по `ark:tribe:*:structure:*` (или по индексу трайбов, если их много
   и полный `SCAN` станет заметен) с `dirty = "1"`.
2. `INSERT ... ON CONFLICT (tribe_id, map_id, struct_key) DO UPDATE` в
   `structure` — один upsert на изменённую постройку, не на каждый снимок:
   если постройка не менялась между двумя прогонами задачи, писать нечего.
3. Сбросить `dirty` в Redis после успешной записи в Postgres, не до —
   иначе упавшая посреди прогона задача потеряет изменение, которое никогда
   не попадёт в Postgres.
4. Постройки трайба, не тронутые дольше `stale_after` (UC-1) — `status =
   'possibly_demolished'`, тем же прогоном или отдельным более редким.

### 8.4 Что закрывает эта схема из первоначального предложения

Твоя идея подтверждается с одной поправкой: живые сущности (не только
игроки — и дино тоже, раз они наблюдаются тем же путём) в Redis без
Postgres вовсе, структуры — Redis как write-buffer, Postgres — периодический
durable-снимок. Поправка — по ключу: не на клиента-репортёра, а на саму
сущность, иначе два клиента, видящие одного врага, продублируют его в двух
разных записях вместо одной актуальной.

## 9. Открытые вопросы (нужно решение владельца продукта, не инженерное)

1. **Нужна ли история перемещений союзников (UC-2)?** Текущая версия —
   только Redis, TTL, без durable-копии: видно «кто где сейчас», нельзя
   посмотреть «где был вчера в 22:00». Если такая история нужна (разбор
   рейдов, статистика активности) — добавить таблицу, дозаписываемую из
   `ark_relay`; если нет — текущая схема (§8.1) уже полная, ничего добавлять
   не нужно.
2. **UC-3 целиком** — записывать ли позиции противников вообще. Технически
   можно (см. §5.4), но это меняет природу инструмента: из клиентского ESP
   в расшаренный между трайбом трекинг чужих позиций (см. предыдущее
   обсуждение). Документ описывает *как* это было бы устроено, если решение
   — делать; не является рекомендацией делать.
3. Что считать «расшариванием ключа» на уровне фингерпринта (см. отдельный
   AUTH-документ) — не блокирует телеметрию, но `client_id` в каждом снимке
   становится источником данных для этой проверки, и стоит решить до того,
   как накопится история, которую потом придётся ретроактивно размечать.
4. ~~Формат `map_id`/`server_id` (A2)~~ — **частично решено в v2**: живая
   раздача `ark_relay` (§7.2/§7.3, §8.1a) больше не ждёт стабильного
   `server_id`/UUID от клиента вообще — маршрутизация и дедуп-ключ работают
   на `server_ip` (реальный IP:port игрового сервера, а не человекочитаемое
   имя), которое клиент узнаёт сам при подключении к серверу. Резолвинг
   `server_ip` → `server_id`/`Server`/`GameMap` (UUID, имя, код карты) через
   A2S_INFO-запрос — задача `backend_python`-консьюмера (§8.1a), не клиента
   и не `ark_relay`. Открытым остаётся то же самое для архивного/HTTP-канала
   (§1-6, `POST /v1/telemetry/structures` и далее) — там клиент по-прежнему
   должен явно передавать `map_id`, эта часть A2 не затронута v2.
